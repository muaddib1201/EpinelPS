# 持续成长的托管 NPC 玩家

状态：用户已于 2026-11-06 确认按设计直接实现。实现、独立审阅、全套回归和本机安装已完成；已生成 30 名 NPC、3 个联盟并通过在线只读核验。客户端画面验收待用户重新进入游戏。

## 已确认的需求

用户希望创建一些托管的 NPC 玩家。他们各自拥有初始游戏进度、角色与联盟，并且之后持续成长。用户已选择“服务端规则托管”，优先做出持续活动的玩家和联盟生态。

## 方案选择

1. **服务端规则托管（用户已选择）**：服务端按个人节奏模拟推图、养成与联盟活动，把结果保存到独立存档。无需运行额外客户端，成长行为可以配置和暂停。
2. 完整流程代玩：逐项遵循玩家资源收支、玩法解锁与操作流程，需要更多玩法补全和战斗判断，开发量较大。

第一版沿用现有 C# / ASP.NET Core 服务端、JSON 游戏存档和 SQLite 玩家资料，不增加外部 AI 服务。这是实施者根据现有项目作出的技术选择。

## 第一版默认效果

以下数量和节奏是实施者提出的默认值，尚待用户随设计一起确认；后台可以调整。

- 首批创建 **30 名 NPC、3 个新联盟**。每个联盟初始 8 名 NPC，另有 6 名暂未加入联盟的 NPC。
- NPC 有不同的自然昵称、头像、简介、角色收藏和代表队伍；后台明确标识为托管 NPC。
- 初始进度分为新人、普通活跃玩家、老玩家三个档次，普通主线约分布在第 3～24 章；等级、角色和关卡均限于当前游戏数据表的有效范围。
- 各 NPC 的角色等级、技能、收藏数量和关卡进度与档次相匹配，避免所有玩家都采用同一个阵容或成长数值。
- 三个新联盟分别偏休闲、日常活跃和养成，采用合法的独立名称与图标，由 NPC 担任会长。联盟可被推荐、搜索、查看资料和成员。
- 真人玩家可以加入满足条件的开放联盟、退出非会长身份的联盟。为此补齐当前缺少的基本加入与退出流程，不自动更改真人玩家现有联盟。
- NPC 日常参与联盟活跃和已实现的射击场榜单，分数由阵容和战力规则模拟生成。
- 暂未入盟的 NPC 可以在后续活跃时加入尚有空位的 NPC 联盟；默认不会自行加入真人创建的联盟。后台可以把指定 NPC 调入选定联盟。

## 持续成长规则

- 增加服务端后台任务，每分钟检查一次到期 NPC；不为每个 NPC 新建线程或启动游戏进程。
- 每个 NPC 持久保存随机种子、成长档次、活跃时间段、下次行动时间、上次实际活动时间和当日额度。
- 行为间隔约 20～90 分钟，在各自的活跃时间内错开。推图、角色成长、角色招募和联盟活动使用不同频率。
- 新人、普通、活跃三档的普通主线推进上限默认为每天 4、8、12 个有效主线战斗关卡；实际行动受角色成长和目标关卡条件限制，可以出现停滞。
- 指挥官与角色成长设置每日上限，并随所处阶段放缓。技能提升和新增角色更少发生，不在每次轮询时全体同步升级。
- 只选择当前数据表中的有效角色、关卡、装备、技能等级、联盟等级与射击场项目。不采用简单的关卡 ID 自增。
- 进度更新同时维护已完成关卡、最后主线关卡和相关的展示状态；代表队伍引用真实拥有的角色序号，展示战力使用现有计算方式。
- NPC 存档包含需要展示的养成结果；这一版不承诺模拟玩家所有任务奖励、抽卡付费或完整资源经济。
- 重启之后按保存的时间继续。离线追赶最多模拟 72 小时，且仍受逐日额度限制；更早的时间跳过。全局或单个 NPC 暂停期间不累计待追赶行动。
- 对同一时间段重复轮询、重试或重启不得重复推进、重复增加联盟贡献或重复生成射击场记录。系统时钟回退不得让进度倒退或重发额度。
- 在线与最后活动显示依据保存的活动时间，不把所有 NPC 伪装成永久在线。

## 数据与持久化

现状：`User` / `CoreInfo` 保存在 `db.json`；昵称和简介位于 SQLite 的 `GameUser`；联盟成员从 `User.Guild` 汇总。资料页依赖两边都有相同的用户 ID。

- 复用现有 `User` 游戏数据和 `GameUser` 资料行；新增可选的 NPC 状态和全局托管配置，旧存档缺少字段时仍可正常加载。
- **不为 NPC 创建 `SdkUser` 登录账户或登录凭证**。因此 NPC 通过新增的 NPC 后台管理，普通登录账户列表不需混入虚拟邮箱。
- NPC 和 NPC 联盟有明确的持久标记。不能仅凭昵称、账号数量或联盟名称推断某个对象属于托管系统。
- 初始创建与增加 NPC 使用稳定批次标识和用户 ID，预留 ID 时同时检查 JSON、SQLite 和待完成创建记录，防止重复创建或冲突。
- 创建涉及 JSON 与 SQLite 两处存储，需要可恢复的创建记录：先持久记录待创建对象与稳定 ID，再幂等补齐资料行和游戏数据，完成后标记提交。启动时只修复这些已明确标记的未完成批次。
- NPC 的日常成长、额度和联盟分数尽量在一次现有原子 JSON 保存中提交；保存失败回滚本次内存变更，不留下“内存已成长、磁盘没成长”的状态。
- NPC 推图模拟不直接复用会跨存储写入真人任务触发器的 `ClearStage.CompleteStage`；提取或编写只处理 NPC 存档的转换逻辑，复用有效数据表和计算规则。NPC 不产生无用的真人任务触发器。
- 后台任务使用独立依赖注入作用域/数据库上下文，不从工作线程使用 `GameContext.Instance`。
- 与资料页、联盟成员和榜单读取统一锁顺序。列表迭代与 NPC 创建不能并发修改同一集合；应审查相关读取入口，避免死锁及集合修改异常。

## 联盟与射击场

- 基本加入/退出使用已有协议消息和错误枚举。加入检查是否已有联盟、内容解锁、等级限制、成员上限、开放状态及已有退盟冷却；退出保留协议需要的时间。
- 真人会长退出、转让、解散、审批制申请等完整管理功能不在本版范围；无法执行的请求返回协议错误，不能假成功。
- NPC 联盟采用开放加入。NPC 会长保持稳定，不自动解散或把真人踢出联盟。自动入盟只在标记的 NPC 联盟内进行，不因后台任务把真人跨联盟移动。
- 联盟经验、人数上限和等级从游戏数据表读取；需要时补充现有 `GameData` 表加载。NPC 活跃贡献按每天唯一额度计算，不能因一分钟一轮检查而无限刷取。
- 射击场使用现有保存结构和排名规则，生成少量与 NPC 阵容、战力及项目匹配的模拟成绩与快照。仅正常项目进入联盟榜单，固定规格练习规则保持一致。
- 已实现的射击场榜单可随 NPC 成长变化。当前竞技场、全服成长榜、好友系统和联盟突袭仍有未完成逻辑，不把这些功能纳入本版，不声称生成 NPC 就能开放这些玩法。

## 管理入口

在现有管理后台增加“托管 NPC”入口，并沿用管理员认证与表单防伪校验。

- 显示 NPC 数量、所属联盟、成长档次、等级、主线进度、最后活动、下一次行动和运行/暂停状态。
- 首次一键按默认方案生成；后续可增加 NPC、修改全局速度、全局暂停/恢复、单个暂停/恢复、调整指定 NPC 的成长档次与所属联盟。
- 默认允许总数 1～200，速度倍率 0.25～4。数量上限与倍率是保护运行成本和方便调试的实施者选择。
- 不自动删除 NPC。用户在后台调整配置或添加 NPC 不得重置已经存在的 NPC 进度。
- 提供可检查的最近行动记录，并限制每个 NPC 最多保留 50 条；射击场历史沿用既有 100 条上限。

## 验证与安装

- 全部功能验证先使用隔离的测试 JSON 与 SQLite，不能在测试中连接当前真实存档。
- 重点验证创建幂等性、跨存储创建中断恢复、UID 冲突、不同初始档次、代表队伍有效性、每日成长上限、跨日/重启/离线追赶、暂停语义与保存失败回滚。
- 验证资料页、联盟推荐/搜索/详情/加入/退出、成员数据和射击场榜单在 NPC 更新后读取一致；验证未登录、非管理员和无防伪令牌的后台写操作不能生效。
- 对新增的共享集合写入做有针对性的并发验证；运行现有联盟与射击场回归，确认此前修复仍然有效。
- 从当前完整源码发布；安装前备份当前程序、配置及一致的 JSON/SQLite 存档。保留已有配置与其他修复。
- 只有在客户端和服务端均安全停止之后替换程序及生成首批 NPC；若客户端仍在运行，准备好安装包和脚本，等待关闭后完成。
- 自动验证和安装结果与客户端验收分开报告。客户端最终需确认能看到 NPC 资料、加入 NPC 联盟、查看队伍和榜单，并在后续活动后观察到进度变化。

## 留给实施者的选择

具体类名、路由在已有协议内的映射、NPC 自然昵称库、三个联盟名称、各档次的细部数值和后台页面布局由实施者根据现有代码决定。不得因此扩大到竞技场、好友聊天或完整资源经济系统。

## 完成标准

首批 NPC 有彼此独立且重启后仍保留的存档和联盟归属；服务端持续运行时，能按不同节奏推进并保存；真人能够查看他们并加入开放的 NPC 联盟；管理员可以查看、配置和暂停托管；旧玩家数据与已有功能通过相关回归。
