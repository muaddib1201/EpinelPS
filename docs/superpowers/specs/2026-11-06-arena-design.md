## 目标与范围

让现有真人玩家能在原版客户端中进入新手与特殊竞技场，看到持续成长的托管 NPC，设置进攻、防守阵容，发起实际战斗，保存胜负、排名、次数和奖励。复用当前完整源码的其他修复与已有 JSON / SQLite 存档。

冠军竞技场的分组、投注和淘汰赛不在用户选定范围内。没有原始战斗录像时，不把空链接伪装成可用回放。

## 实现方式

1. **沿用客户端战斗（采用）**：已有协议提供 `/arena/start`、`/arena/result` 和特殊竞技场的客户端模拟模式。服务器发送真实角色、装备、魔方与养成快照，客户端运行原版战斗，服务器绑定开始与结果并结算。这与现有战斗玩法一致，可以保留观看战斗与真实技能效果。
2. 按战力公式直接决定胜负：实现较少，但无法提供真实战斗，与本次完整挑战流程不符。
3. 新建服务端战斗引擎：目前项目没有相应引擎，需要额外复现技能和战斗运行时，不适合当前增量补齐。

技术选择由实施者根据现有源码作出：继续使用 C# / ASP.NET Core、Protobuf、JSON 原子存档和现有 SQLite 玩家资料，不引入网络服务或依赖。

## 入口与阵容

- 去掉新手、特殊竞技场的 `Not Implemented` 禁用响应；冠军仍明确不可用。
- 入口提供有效服务器编号、本人排名/段位、日次数、赛季日程，以及协议要求的防守队伍。
- 使用当前数据表的 `ArenaTable`、`TierTable`、`ArenaRewardTable`、`TimeStackRewardTable` 与相关配置；表字段不足的本服默认值要明确记录。当前包的 Arena/Tier 表只有特殊竞技场，新手免费次数使用仍存在的 `ArenaTodayMaxCount=3`，不伪造不存在的新手段位表；入口与战斗的实际客户端兼容性需要验收。
- 普通竞技场进攻/防守使用 TeamType 4/3；特殊竞技场使用 13/12，每侧三队，队号和槽位沿用客户端协议。
- 阵容仅允许拥有的角色，槽位与队号有效，不允许支援角色；同队不能重复，同一特殊竞技场三队不能重复角色或同名角色的不同实例。
- 旧玩家未编队时可生成合法默认队伍，但后续读取不能覆盖其手动保存的有效队伍。
- NPC 防守从实际拥有角色中选择并错开三队；角色不足 15 名的 NPC 不能凭空复制角色补位，只参与其能够合法组成的玩法。阵容选择优先保证爆裂阶段覆盖，并使用角色当前养成展示战力。
- 保存竞技场队伍时使用统一存档锁，并在保存失败时恢复；不改变其他玩法的编队行为。
- 竞技场魔方使用独立持久配置；首次从现有魔方装备复制，之后竞技场穿戴/卸下/批量管理不改变普通编队配置。补齐协议中的三个竞技场魔方入口及登录、背包、魔方查询中的 ArenaHarmonyCubes。

## 对手与排名

- 同一私服使用一个竞技场分组，排除本人、被封禁玩家和没有合法防守队伍的玩家。暂停成长的 NPC 仍可以作为已存在的防守者。
- 对手列表按当前排名与战力选取少量可挑战对象；支持重复刷新，不创建额外虚构 Bot，不把托管玩家标为客户端内置 Bot。
- 新手竞技场按评分降序、稳定 ID 次序排序，挑战成功加分、失败扣分，防守方相反；评分变更有下限。
- 特殊竞技场持久保存唯一战斗排名；胜过更高排名的对手时交换双方名次，挑战更低排名或失败不提升名次。三局两胜；无效、重复或矛盾的局次结果拒绝结算。
- 首次排位按防守战力降序和用户 ID 确定，新加入者追加至榜尾；双方换位前先按旧段位累计至当前时刻。
- 提供双方资料、完整敌队、榜首、特殊竞技场积分榜、双方近期攻守记录；记录数量使用表中上限。
- NPC 成长通过每次开始时生成的新快照生效，已开始的战斗保留原快照，避免中途养成改变敌人。

## 战斗、次数与一致性

- 开始前校验解锁进度、对手和有效进攻/防守队伍。每日免费次数按当前表，之后只消费已有竞技场票；不隐式扣钻石购买。
- 开始时持久保存战斗编号、对手、模式、快照、开始时间、随机数、已扣次数/票。一次只允许一个未完成战斗；超时战斗按已消费挑战处理，不能通过放弃无限试打。
- 相同开始包重试必须返回相同快照，不重复扣次数；结果只允许结算已开始的本人战斗，不能通过请求里的敌方快照修改存档。
- 使用用户、路由、传输包 Nonce 保存回执（最近 128 个及最近两日全部回执），并保留紧凑的已处理身份/正文指纹。响应过期后旧包明确拒绝，同 Nonce 改正文也拒绝。独立审阅和故障测试确认：无 Nonce 的旧结果无法与下一场同目标战斗区分，因此开始/结果必须携带正常加密包已有的传输 Nonce；缺少时明确拒绝，不猜测战斗归属。
- 结果保存持久回执。相同结果重试或进程重启后重试返回原响应，不重复评分、交换排名、发奖或添加记录；没有开始、错误对手、过期与矛盾结果返回明确协议/HTTP 错误。
- 读写使用 `JsonDb.SaveLock`，涉及本人锁时遵守现有 `user -> SaveLock` 顺序，不交叉锁定第二名玩家；所有 JSON 变更一次保存，失败恢复双方与奖励状态。
- 以可注入时钟处理每日重置，保持单调时间水位；回拨时间不重发次数与时间奖励。
- 特殊竞技场明确返回 Client 模拟模式；v2 服务端模拟请求缺少胜负结果，返回明确的不支持错误，不凭战力伪造服务端模拟结果。
- 竞技场次数/胜利相关任务通过现有触发器机制更新，采用持久待交付记录避免 JSON 与 SQLite 跨存储中断造成重复或丢失。

## 奖励与赛季

- 新手胜利奖励按当前竞技场奖励表/条件奖励表写入真实钱包或道具，响应与存档一致。
- 特殊竞技场依当前段位累积竞技场票与排名积分，沿用表中时间间隔，显示、领取、历史和积分榜都来自同一存档；领取后不能重复领取。
- 为离线服提供确定且可持久追踪的本地赛季日程，按现有表提供的周期/配置或记录明确的本服周期。日/赛季排名奖励按快照结算为可领取奖励，不能在每次打开页面时重复发放。
- 当前包没有完整运营赛季，使用从 **2026-11-05 20:00 UTC（北京时间 2026-11-06 04:00）** 起算的连续 14 天本服赛季；结束前开始、结束后提交的在途战斗拒绝结果并保留已消费次数。赛季结算只处理实际已创建的赛季，不追溯生成系统上线之前的奖励。
- 赛季结算在锁内统一处理，跨日/重启/长时间离线/时间回拨均须验证；不伪造官方运营赛季和服务器模拟回放。
